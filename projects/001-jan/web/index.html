01 / 产品定位我们的理解汇总

Jan 是一个类 ChatGPT 的
开源桌面 App。

它提供聊天与助手界面，组织上下文，接入本地或云端模型，并处理模型反馈。任务需要采取行动时，Jan 再执行工具或派发子任务。

JAN 负责组织与执行

界面、上下文、工具、数据与运行管理

模型负责理解与生成

理解输入、生成回答、提出操作和下一步判断

“类 ChatGPT”描述产品形态，不代表已证实沿用其内部架构，也不代表具有同等模型效果。

02 / 基础链路

先看一条链路，再看整个软件。

普通聊天由下面五步组成。上下文包含当前消息、必要的历史、角色指令，以及按需检索到的资料或记忆。

  1. 01用户输入问题、任务、附件
  2. 02组织上下文筛选、召回、压缩
  3. 03模型适配模型、参数、协议
  4. 04模型推理本地或云端计算
  5. 05处理反馈展示、保存或执行
↺
Agent 模式多了一次执行循环

模型提出操作 → 检查执行条件 → 调用工具或子 Agent → 结果加入上下文 → 再次调用模型。

记忆只是上下文的一种来源。保存了资料，不意味着每次都要把全部资料发送给模型；角色配置也不等于子 Agent 调度。

04 / 价值与边界

替代一种使用方式，借鉴一套工程思路。

对使用者

多一条 AI 使用路径

无法访问 ChatGPT、网络受限，或希望本地处理资料时，可选择适合任务的本地模型。用户也可以更换模型服务、查看源码并修改软件。

离线使用需先备好模型与依赖；云模型、搜索和远程工具仍需联网。实际能力取决于模型及配置。

对开发者

研究应用怎样被组织起来

优先看服务抽象、模型适配、文件与设置、下载、升级和工具接入。后续再深入检索、记忆、Agent 主循环和子任务调度。

当前开发分支确有子 Agent 派发和并发管理实现，成熟度尚未在本次研究中验证。

我们可以沿主链路开发，按需求扩展。

界面 / 执行业务 / 模型适配上下文 / 存储模型决策 / 工具执行

先理清这些边界，再增加模块。每次扩展都明确：它接在哪里、保存什么状态、失败时怎么办。通用能力可以支撑通用工作台，也可以承载某个任务流程。

05 / 我们希望探索的方向

实现软件，也把工程过程
呈现出来。

让访问者既能使用功能，也能看清能力如何拆解、模块如何协作、设计为何这样选择。以实际代码和运行结果为讨论基础。

能力地图→模块职责→接口与源码→运行过程→设计取舍
01

可以学

从主链路走进模块，理解接口、状态和数据流。

02

可以借鉴

找到可复用的实现，同时知道依赖和适用边界。

03

可以讨论

围绕设计选择、故障行为和验证结果展开交流。

例如：做深一个下载模块

实现下载功能的同时，展示它与应用升级的分工、暂停与续传的状态转换、网络中断的恢复、校验失败的处理，以及可复用的接口。

这是我们提出的项目方向，不是 Jan 的官方定位。学习、作品展示和技术交流是可能的价值，商业需求仍需验证。

推进顺序

一条链路做完整，一个模块做深入。

  1. 先跑通输入到反馈

    展示主链路与接口边界。

  2. 再做稳保存、错误与取消

    解释状态归属和失败处理。

  3. 选一个做深文件、下载或工具

    提供源码、运行记录与取舍。

  4. 按需求扩展检索、记忆、子 Agent

    验证数据流、权限与并发。
