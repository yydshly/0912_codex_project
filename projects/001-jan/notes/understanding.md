# 对 Jan 的理解与我们的研究方向

> 核心定位：**Jan 是一个类 ChatGPT 的开源桌面 App。** 它提供聊天与助手界面，组织上下文，连接本地或云端模型，并处理模型反馈；在需要时执行工具和子任务。

本文汇总我们围绕 Jan 的讨论。“Jan 的现有能力”以固定提交的源码研究为依据；“我们的方向”是后续项目设计思路，尚未实现或验证。

## 1. 这个库本质上是什么

Jan 属于 AI 应用层。它把模型能力包装为用户可以直接操作的桌面软件，包含会话、助手、项目、资料与工具等功能。用“类 ChatGPT 的 App”描述产品形态，比仅称为模型适配器或角色管理界面更完整。

这里的“类 ChatGPT”表示相似的聊天与助手使用方式，不表示已经证实它沿用了 ChatGPT 桌面端的内部架构，也不表示模型效果等同。

| 组成 | 负责什么 |
| :--- | :--- |
| Jan 应用 | 界面交互、上下文组织、模型适配、工具执行、数据保存、运行与交付管理 |
| 所选模型 | 理解输入、生成内容、提出工具操作及下一步判断 |
| 推理引擎 / 云服务 | 实际执行模型计算，并返回生成结果 |

当前研究重点是 `janhq/jan` 这个应用代码库，而不是 Jan 品牌下其他模型或服务的全部能力。软件许可、模型许可与云服务使用条件也需要分别理解。

## 2. 核心是一条基础链路

**用户输入 → 组织上下文 → 模型适配 → 大模型推理 → 处理反馈 → 展示与保存。**

“上下文”比“记忆”更准确：它包含当前消息、必要的会话历史、角色指令、项目说明，以及按需检索到的文件或长期记忆。保存了某项数据，不意味着每轮请求都要发送它。

普通聊天可以沿着这条链路完成。Agent 模式增加循环：

**模型提出工具操作 → Jan 检查执行条件并执行 → 将结果追加到上下文 → 再次调用模型 → 继续处理或结束。**

角色助手主要是保存系统指令与参数；子 Agent 还涉及独立运行、派发、并发管理、结果回收和取消处理。两者不应混为一谈。

## 3. 其他模块怎样围绕链路展开

| 目的 | 相关模块 | 与主链路的关系 |
| :--- | :--- | :--- |
| 让用户能够使用 | 桌面界面、会话、助手、项目、附件 | 承接输入，组织工作空间，呈现结果 |
| 给模型提供信息 | 文件解析、检索、历史、长期记忆、技能 | 为上下文提供必要材料 |
| 让模型可以运行 | 模型适配、本地引擎、下载、导入、硬件检测 | 准备模型资源并执行推理 |
| 让任务能够行动 | MCP、本地工具、权限、Agent 循环、子 Agent | 执行模型提出的操作，并回传结果 |
| 让软件持续可用 | 文件系统、持久化、配置、凭据、升级、日志与发布 | 支撑整体应用，不是每轮对话的必经步骤 |
| 让架构可扩展 | 服务抽象、扩展注册、本地 API、CLI | 复用能力并隔离界面、平台与模型差异 |

模块职责要分清：模型下载与应用升级不同；文件存储与文档检索不同；角色配置与任务调度不同。当前提交已含子 Agent 后台派发和并发控制实现，但本次未验证运行成熟度。

完整的十八项模块及源码入口见[能力模块架构研究](architecture.md)。

## 4. “ChatGPT 的开源替代品”意味着什么

Jan 提供另一种 AI 使用方式：用户可以选择模型、本地保存数据、查看或修改源码，并把能力接入自己的工具。无法访问 ChatGPT、网络受限，或希望本地处理资料时，本地模型路径可能有实际价值。

需要区分三个维度：

| 维度 | 应如何理解 |
| :--- | :--- |
| 产品体验 | 能提供相似的对话、资料问答和助手交互 |
| 控制权 | 可以选择模型、运行方式、数据位置和软件修改方式 |
| 智能水平 | 取决于模型、硬件、上下文与工具配置，不能由“替代品”这一定位直接推出 |

离线使用需要提前准备模型与必要依赖，选用本地模型和本地工具；云模型、网页搜索和远程服务仍需要网络。它不是访问不可用云服务的绕过工具。

## 5. 对我们有什么研究价值

Jan 适合作为 AI 桌面应用与任务执行系统的工程参考。优先研究接口边界、状态归属、资源生命周期和错误处理。

| 现在值得参考 | 后续按需求深入 |
| :--- | :--- |
| UI 与执行分离、ServiceHub、模型适配 | 文档解析、RAG、长期记忆 |
| 文件与业务数据、设置与凭据 | 工具权限、任务执行和上下文压缩 |
| 大文件下载、应用更新 | 子 Agent 派发、并发、取消及结果回收 |

可以用主链路搭建最小系统，再逐步增加功能。每加一个模块，明确它接在哪里、拥有何种状态、失败时怎么办。通用接口值得提前理清，尚无需求的模块不必提前实现。

当前源码中的细节也提示我们不能直接照搬：例如主 Agent 循环里的 token 预算超限会记录提示并继续运行，不能当作强制成本上限。具体分析见[研究笔记](architecture.md)。

## 6. 通用软件与垂直产品如何理解

Jan 本身是通用 AI 工作台。聊天、模型接入、资料、记忆和工具都是通用能力；通用产品可以依靠易用性、兼容性、稳定性与本地控制来提供价值，并非必须为单一行业定制。

通用底层也可以承载特定工作流程。定制通常发生在材料输入、处理步骤、工具连接、结果检查和交付形式上，仅换一段角色提示词通常不足以构成完整的专用产品。

对我们而言，继续增加聊天、记忆或 Agent 功能并不能自动建立产品差异。需要明确别人为何使用、为何复用，以及我们带来了什么可检查的结果。

## 7. 我们希望探索的方向：实现软件，也公开呈现工程过程

**围绕真实 AI 应用，公开呈现架构、模块实现、运行过程和设计演进。**

我们希望把实际软件与研究表达连接起来，让访问者既能看到系统能做什么，也能理解它为什么这样设计，并据此复用模块或讨论技术。

这是一项待实践的定位，而不是 Jan 官方定位，也不代表已经验证商业需求。

| 我们希望提供的价值 | 应交付的内容 |
| :--- | :--- |
| 学习价值 | 主链路、模块职责、接口边界和可追溯源码 |
| 工程参考价值 | 可运行的模块、状态机、异常处理、复用条件 |
| 技术讨论价值 | 设计选择、替代方案、验证结果和局限 |

呈现路径是：**能力地图 → 模块职责 → 接口与源码 → 运行过程 → 设计取舍。**

透明化的重点是设计与真实实现保持一致。公开架构图只是开始，图中模块应当能追到代码，并能通过实际行为说明其能力和边界。

以“下载模块”为例，除了完成下载功能，还可以同步交付：为什么和应用升级分开；暂停、续传、取消的状态转换；网络中断或校验失败的行为；进度与日志的展示；平台依赖与可复用部分。

## 8. 后续推进顺序

| 阶段 | 软件产出 | 同步呈现的研究内容 |
| :--- | :--- | :--- |
| 先跑通 | 输入、上下文、模型调用、反馈 | 基础链路和接口边界 |
| 再做稳 | 会话、配置、错误处理、取消 | 状态归属、持久化和失败处理 |
| 选一个模块做深 | 按实际需要选择下载、文件或工具接入 | 源码、状态图、运行记录与设计讨论 |
| 再扩展 | 按需求加入检索、记忆、子 Agent | 数据流、权限、并发与结果验证 |

早期可以观察是否有人沿图读代码、复用模块或提出具体技术问题。学习、作品展示和社区交流是可能的价值，商业价值仍需另外验证。
