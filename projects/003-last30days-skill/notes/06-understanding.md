# 我们的理解：预设平台与接入方式，按问题编排研究

研究日期：2026-09-11。上游为 [mvanhorn/last30days-skill](https://github.com/mvanhorn/last30days-skill)，结论固定于 v3.24.0 / [ca9d415e66073b17702f385d6886934097aec0e7](https://github.com/mvanhorn/last30days-skill/commit/ca9d415e66073b17702f385d6886934097aec0e7)。状态：源码梳理与离线评估已完成，真实多源联网效果待验证。

## 1. 库的本质原理

**开发者提前选定支持的平台，为每个平台实现搜索、认证、正文 / 评论 / 字幕获取和结果转换；用户提出问题后，模型与程序在这套已有能力中安排检索，收集并清洗证据，最后生成研究报告。**

因此，理解它应分成两段：

1. **提前建设能力：** 接入哪些平台 → 用什么方式访问 → 支持哪些搜索和详情操作 → 结果怎样变成统一证据。
2. **运行一次研究：** 用户问题 → 理解对象与意图 → 生成查询和来源计划 → 调用平台适配器 → 补取内容 → 筛选、去重、排序 → 形成证据与回答。

它把已有模型、平台接口、采集工具和研究规则组织成可执行流程。普通研究任务调用的是已经实现的接入能力；输入一个此前未接入的网站地址，并不会自动获得该站专用的登录、搜索、评论和字幕采集功能。

## 2. 提前设置什么，运行时决定什么

| 层级 | 提前具备的内容 | 收到问题后发生的事情 |
| :--- | :--- | :--- |
| 平台支持 | Reddit、X、YouTube、HN、GitHub 等来源适配器 | 从已接入来源中安排检索 |
| 接入方式 | API、RSS / 页面、登录会话、第三方服务、CLI、本地读取 | 按对应方式发请求，处理认证、时间、分页、限量与回退 |
| 搜索经验 | 平台能力、来源优先级、意图规则、领域社区名单和 Skill 指令 | 结合主题选择查询角度、关键词、账号、社区或仓库 |
| 运行配置 | 工具安装、来源开关、凭据、本地服务和可选资料目录 | 判断哪些来源允许使用、有条件调用；请求后记录真实状态 |
| 统一处理 | 数据结构、去重、融合排名、重排、聚类与输出逻辑 | 把不同平台结果转换、筛选并组合为证据 |

**“平台和接入方式预先实现”不等于“每次研究的账号和关键词提前写死”。** 平台可以固定支持 GitHub，但本次查哪个仓库、用哪些问题词，仍可以由用户指定或模型先解析。Telegram 等来源则可能要求事先提供明确的公开频道名单。

源码中，`pipeline.available_sources()` 形成可用来源集合；`planner.py` 保存来源优先级、能力和规划约束；各平台模块负责实际请求和内容转换。配置只是启用、选择或提供凭据，专用接口能力来自已经写好的实现。[来源调度][pipeline]、[规划器][planner]、[配置说明][config]。

## 3. 它怎么知道去哪里搜、怎么搜

这由 **作者的规则 + 模型对问题的理解 + 当前可用能力** 共同决定。

- **作者提供平台知识。** 例如教程可从 YouTube / Reddit 找，项目维护与问题讨论可从 GitHub 找。相关经验写入 Skill、能力标签、优先级与领域分类。
- **模型把问题变成计划。** 识别同名对象、别名和账号，把一个问题拆成若干子查询，生成搜索词、排序问题和来源列表。
- **程序决定怎样执行。** 校验计划、应用用户范围和预算，通过已写好的适配器发出符合该平台要求的请求，再按返回的 ID 或链接补取详情。

平台选择并不总是“模型挑出最相关的两个平台”。主查询可以覆盖多个适用来源；内部规划器的非快速路径还可能按规则扩展覆盖，再由后续排序筛选证据。显式传入的外部计划会保留其逐子查询来源，但仍受可用性和预算限制。没有规划模型时，部分路径可以按固定规则回退。[规划与校验][planner]、[上层搜索指令][skill]。

例如，用户输入“某开源数据库最近 30 天的维护变化与用户问题”。上层先确定项目名和仓库，再生成维护、故障、使用反馈等查询；GitHub 适配器调用 REST 接口，HN 适配器调用 Algolia，Reddit 适配器调用 RSS / 页面等路径。各适配器收到同一个研究方向，但使用各自已经实现的访问方式。此例是流程说明，未执行联网搜索。

## 4. 接入平台与对应获取方式

以下是固定版本的能力概览；**存在实现不等于本机已启用或当前访问一定成功**。详细端点、认证条件、备援顺序和源码链接见 [完整来源与内容矩阵](03-source-and-content-matrix.md)。

| 平台 / 来源 | 已实现的获取方式 | 内容深度要点 |
| :--- | :--- | :--- |
| Reddit | RSS / shreddit 页面 + Arctic Shift；ScrapeCreators 备援 | 帖子、互动指标；选定帖子的评论正文 |
| X / Twitter | 默认候选链 Bird 登录会话 → xAI → xurl OAuth CLI → Xquik；另有显式后端 / 宿主连接器路径 | 推文及互动；可搜到回复，不能据回复数认定取得完整对话树 |
| YouTube | yt-dlp 搜索、元数据、字幕和评论；条件性 HTTP / ScrapeCreators 备援 | 现有人工 / 自动字幕、选定视频的少量热门评论 |
| TikTok、Instagram | ScrapeCreators 搜索与转录 / 评论接口 | 描述、转录文字、互动和有限评论，受配置与返回内容限制 |
| Hacker News | Algolia 搜索与条目 API | 讨论条目及选定评论 |
| GitHub | REST 搜索 / 对象接口；可匿名或使用 token | Issue / PR、选定评论，以及特定模式的项目 / 人物活动 |
| LinkedIn、Threads、Pinterest | ScrapeCreators API | 帖子 / Pin 等可用文字和互动，不能默认推断完整评论正文 |
| Telegram | ScrapeCreators 公开频道接口 | 按指定频道取帖子，未实现全站关键词发现 |
| Bluesky、Truth Social | AT Protocol + 应用密码；Truth Social API + token | 帖子文字和互动 |
| 小红书 | 本地已登录 MCP 配套 HTTP 服务 | 当前主要取搜索卡片和计数，未调用笔记详情 / 评论正文接口 |
| Digg、arXiv、Techmeme | 各自的 Printing Press CLI | 聚合内容、论文元数据 / 摘要、技术新闻 |
| Polymarket、StockTwits、DripStack | 各自公开 API；部分来源按主题或显式配置启用 | 市场信号、金融消息 / 情绪和文章结果 |
| Trustpilot、Amazon | trustpilot-pp-cli；Bright Data CLI | 企业评价、商品信息及评论样本，依赖相应配置 |
| 招聘页、本地资料 | 公开 ATS API / 网页；文件读取 / PDF 文本提取 | 岗位、本地笔记和文档片段 |
| 普通网页、检索服务 | 宿主搜索或 Brave / Exa / Serper / Parallel 等；无密钥 DuckDuckGo / SearXNG + Jina Reader；Perplexity API / OpenRouter 等 | 搜索摘要或正文文字；检索服务需要保留其实际引用的原始来源 |

这里最值得借鉴的是完整的 **“来源 → 获取方式 → 可取内容 → 使用条件 → 失败处理”** 映射。例如，仅写“支持 YouTube”远远不够；要明确能否搜索、能否拿字幕、能否读评论、无字幕时怎么处理、结果是否截断。

评论计数与评论正文必须分开；字幕与视频画面理解也必须分开。当前独立 `transcribe.py` 模块虽然具备无字幕媒体转写能力，但配置文档注明尚未自动接入研究引擎，不能据此宣传主流程能转写任意视频。[来源与内容层级](03-source-and-content-matrix.md)、[上游配置说明][config]。

## 5. 输入、处理、输出及触发方式

| 环节 | 实际含义 |
| :--- | :--- |
| 输入 | 主题 / 问题、对象、时间窗口、深度、可选来源限制和输出要求；也支持显式发起热点发现 |
| 处理 | 解析对象、生成查询、选择可用来源、并发取数、补取部分详情、统一字段、处理日期与相关性、去重、排序和聚类 |
| 引擎输出 | 带来源链接、日期、摘要 / 片段、可用互动指标、来源状态等的证据报告；可输出 JSON、Markdown、HTML 等 |
| 最终回答 | 宿主模型根据证据归纳发现、分歧和限制，写出简报 / 对比表等；单独运行取数程序不等于已经完成模型综合 |
| 启动方式 | 默认由用户或上层任务触发，触发后主动向外取数；周期研究需要另外配置外部调度 |

如果下游要处理评论或字幕，应检查原始研究文本或 raw 输出。稳定 Agent JSON 主要暴露链接、摘要、互动等字段，没有承诺完整评论树与字幕内容。[输入与输出专题](01-input-processing-output.md)、[触发与调度专题](02-trigger-and-monitoring.md)。

## 6. 适用领域与最值得复用的部分

根据内置分类与来源组合，它尤其适合 **AI 工具、开发者生态、技术产品与社区反馈研究**，也可扩展到产品口碑、人物公司、内容趋势与金融情绪。实际质量取决于目标群体是否在已接入来源上公开讨论，以及接口是否能取到足够正文。适用性分析见 [领域专题](04-domains-and-fit.md)。

从实现中最值得复用的部分是：

1. **来源能力与接入方式：** 平台支持什么操作、用哪个后端、有何认证条件、正文能取多深。
2. **统一证据与状态：** 保存原始链接、时间、正文 / 评论 / 字幕区别，以及无结果、限流、认证失败等状态。
3. **研究编排：** 把用户问题转换为可执行的子查询，让模型规划受可用能力、用户范围和预算约束。
4. **内容整理：** 对多个平台、多个查询命中的结果去重和排序，再给模型提供可引用的材料。

可扩展方向属于本研究建议，尚未在本仓库实现：

| 方向 | 需要补上的工作 |
| :--- | :--- |
| 增加新平台 | 实现适配器与认证 / 取数逻辑，注册来源与能力，将结果转为统一证据，验证错误和限流处理 |
| 加深内容获取 | 为只返回搜索卡片的来源补详情 / 评论；完善分页、字幕语言和截断标记 |
| 接入无字幕转写 | 把现有转写模块纳入实际调用链，明确触发条件、成本、时间戳及失败状态 |
| 改善中文与垂直研究 | 扩展来源、别名、社区词表和领域规则，构造真实问题评估覆盖与相关性 |
| 建设持续监测 | 配置外部调度、历史记录、跨次去重、变化摘要、成本记录与失败通知 |

## 7. 本次理解已经验证到哪一步

已核对固定版本源码，并保存一次离线样例的真实输入计划和程序输出；上游离线评估测试 **10 / 10 通过**。这些结果验证固定输入下的处理行为，不证明真实平台的搜索召回、评论 / 字幕完整度或最新接口稳定性。

真实多源联网、付费或登录来源、视频字幕逐条对应，以及周期执行均待验证。样例中的 Nimbus 和 `.example.test` 地址属于上游测试数据，不能当作现实研究结果。全部记录见 [验证与复现](05-validation-and-reproduction.md)。
