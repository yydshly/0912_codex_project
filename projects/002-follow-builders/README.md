# 002 · Follow Builders：预设来源与抓取方式的 AI 简报工具

**Follow Builders 是一个预设来源驱动的 AI 信息简报工具：提前确定支持的平台类型、平台上的具体账号或节目、网站栏目，以及相应的抓取和解析方式，再采集公开内容、过滤去重，交给宿主 AI 生成带原文链接的摘要，供用户阅读或推送。**

它的本质是“配置关注对象 + 对应采集适配器 + 通用内容处理”。关注名单写在 `default-sources.json`；获取和解析方式主要实现在采集脚本中。新增同类账号或节目可以复用已有方式；新增未支持的网站或平台，需要补充适配逻辑。

## 能力速览

| 输入 | 处理 | 输出 |
| :--- | :--- | :--- |
| 人工维护的来源名单 | 找到指定账号、节目、博客的新内容 | 三类公开 JSON feed |
| 原帖、节目转录、博客正文与链接 | 中心去重、时间窗口和数量限制 | 可供模型处理的内容批次 |
| 语言、频率、渠道、自定义提示词 | 读取偏好，选定摘要规则，交由宿主 AI 整理 | 中文、英文或双语简报 |
| 已生成的简报文本 | 按渠道格式发送；Telegram 长文分段 | 聊天输出、Telegram、Resend 邮件；更多渠道依赖宿主 |

来源名单属于输入质量控制，摘要提示词属于编辑规则。当前项目没有训练专用推荐模型，也没有语义搜索数据库或成熟的用户兴趣学习系统。证据定位见[能力与数据流](notes/01-capabilities.md)。

## 已验证的结果与边界

固定提交的公开数据更新时间为 **2026-09-10 06:40 UTC 左右**，X feed 有 **14 位作者、28 条动态**，播客和博客均为 **0**。配置中的来源总数不等于当天有更新的来源数。单批内容为空，不能据此推断整个渠道失效。

本研究对原始 `prepare-digest.js` 做了 8 项隔离核验，全部得到预期观察；其中包括复现现有缺陷，**不是说上游所有功能都正常**：

- 默认路径读取 3 个 feed 和 5 份提示词，共 8 次请求；README 的“一次请求”不符合当前实现。
- 用户提示词能够覆盖远程默认；HTTP 失败可以回退本地，但网络异常会终止流程。
- `daily` 与 `weekly` 取得相同内容，没有一周历史聚合。
- 同一批 feed 反复读取仍返回同样的内容，没有用户级已读去重。
- 三个 feed 都返回 HTTP 503 时，仍输出 `status: ok`，错误在 `errors` 中。
- 博客能进入准备结果，但 Skill 的无内容判断遗漏博客，存在只更新博客时提前停止的风险。

另经源码检查：普通系统定时方案绕过模型，会发送原始 JSON；完整自动简报需要真正调用 AI 的执行器。上游示例含占位链接，不能当作真实产出证明。完整记录见[核验报告](notes/06-verification.md)和[机器可读核验结果](data/verification.json)。

在本子项目目录运行核验：

```powershell
node --experimental-vm-modules scripts/probe-prepare.mjs
```

需要 Node.js 20+ 和访问 GitHub Raw 的网络；本次使用 Windows 与 Node.js v22.15.0。脚本只下载固定提交材料，在虚拟 POSIX 文件系统中执行准备逻辑，不读取真实用户配置，不调用采集服务或发送接口。无需安装第三方依赖。详见[核验报告](notes/06-verification.md)。

## 对我们的直接价值

将 Follow Builders 放在“研究选题发现”这一环：先知道谁发布了值得关注的内容，再定位原始项目、固定版本、复现能力，最终沉淀为本仓库的研究子项目。**feed 中的观点只能提供研究线索，不能替代源码核对和实测。**

优先补充历史存储、完整自动摘要执行、采集失败提示与发送去重；之后再做主题筛选、跨来源事件合并和研究卡片。每阶段的验收标准见[路线图](notes/05-value-roadmap.md)。
