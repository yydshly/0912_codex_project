# 对我们的价值与可扩展方向

研究日期：2026-09-11；依据版本：`c8da0e7ece27d6a0007b53f54f546bf0ff1086d4`。本页是基于前述源码与核验结果的研究判断和建设建议，不是上游已有功能清单。

## 1. 放进我们的工作流，价值在哪里

本仓库研究多个开源项目。Follow Builders 最适合放在研究流程的前端：帮助发现线索，再交给本仓库已有的版本记录、源码分析和复现流程。

```mermaid
flowchart LR
    A[精选来源与公开内容] --> B[发现值得研究的线索]
    B --> C[核对原始仓库和许可]
    C --> D[固定版本并验证能力]
    D --> E[形成编号子项目]
    E --> F[文档、图示与必要的演示]
    F --> G[定期跟踪版本变化]
    G --> B
```

| 可复用资产 | 对我们的用途 | 本次沉淀 |
| :--- | :--- | :--- |
| 人工精选来源 | 建立开源研究的信息入口，减少从零找人的工作 | [34 个来源的元数据](../data/source-catalog.json) |
| 编辑规则 | 让摘要围绕技术、适用场景、复现线索组织 | [研究摘要提示词](../examples/summarize-tweets.research.md) |
| 采集与生成分层 | 相同内容供不同研究方向消费 | [模块与数据流说明](01-capabilities.md) |
| 原文链接与版本记录 | 研究结论可回溯，便于更新时比较 | [证据与核验](06-verification.md) |
| 推送结构 | 将新线索按阅读节奏送达 | [渠道与展示方案](04-presentation.md) |

它提供的是“值得看什么”的候选输入。作者观点、产品宣称、已经公开的代码和我们的实测结论，需要在后续研究中分别标记。不要直接把摘要变成已经确认的技术结论。

## 2. 哪些价值没有必要照搬

- **名单不必全盘采用。** 按我们的主题保留真正提供一手材料的来源，避免多名人物重复谈论同一新闻。
- **消息机器人不是核心壁垒。** 先把内容完整性、来源追踪和研究判断做对，再增加渠道。
- **不宜把当天 feed 当数据库。** 覆盖式文件难以支持完整周报、历史搜索和观点变化分析。
- **不必一开始训练推荐模型。** 显式主题偏好和“有用 / 无用”反馈可以先帮助人工改进名单与规则。
- **博客和播客的空快照不能用于评估长期质量。** 应采集多个周期的结果，再判断来源是否值得保留。

## 3. 选源标准：让名单成为可维护资产

建议每个来源记录以下维度，不预设它们已经达到某个分数：

| 维度 | 判断问题 | 记录方式 |
| :--- | :--- | :--- |
| 一手性 | 是本人构建、维护或研究的成果吗？ | 保留代表文章和对应项目 |
| 具体性 | 是否给出实现、数据、失败经验或可访问产物？ | 有用样本与无效样本各留记录 |
| 主题匹配 | 是否覆盖我们正在研究的方向？ | 主题标签与订阅范围 |
| 独特性 | 相比已关注来源增加了什么？ | 重复事件占比与独立线索 |
| 可获取性 | 能否持续合法、稳定地获得公开材料？ | 获取方式、最近成功时间、错误率 |
| 维护成本 | 是否依赖易变页面或高成本转录？ | 请求数、转录量、人工修复次数 |

先人工复核一段周期的样本，再决定新增、降频或停用；不能只用粉丝数和转发数代替来源质量。

## 4. 分阶段路线与验收标准

### 阶段 A：可信、完整地获取和交付

目的：先确保“没有漏掉、没有伪装成功、没有重复发”。

| 建设项 | 实现方向 | 验收标准 |
| :--- | :--- | :--- |
| 来源配置化 | 将地址、开关、窗口、条数上限从代码常量中抽出 | 修改配置可观察到生效，不必改多个硬编码地址 |
| 历史归档 | 按稳定内容 ID 保存原文指纹、日期、来源、采集时间 | 给定一周窗口能重建完整候选集 |
| 完整生成任务 | 显式串起准备、模型生成、校验、发送 | 自动收到简报文本，不能将原始 JSON 当成功简报 |
| 状态分离 | 采集成功、待重试、已采用、已发送分开 | 暂时失败可重试，成功投递重跑不重复 |
| 失败可见 | 记录每源最后成功时间与错误；保留有效缓存 | 断网、空内容和旧内容可区分 |

这阶段优先针对已复现问题，见[核验报告](06-verification.md)。不要求先做复杂界面。

### 阶段 B：让信息成为研究对象

目的：从“读完一段文字”走向“知道下一步该验证什么”。

| 建设项 | 实现方向 | 验收标准 |
| :--- | :--- | :--- |
| 研究卡片 | 增加主题、原文、研究判断、证据状态 | 每张卡片能解释结论来自哪里 |
| 事件合并 | 按仓库、发布版本、规范 URL 合并，再辅助语义判断 | 同一事件有一个主入口，各原始出处仍保留 |
| 待研究队列 | 从卡片进入候选列表，人工选择后分配稳定项目编号 | 不因重复线索创建重复子项目 |
| 引用核验 | 摘要关键句对应原文片段或代码位置 | 数字、引语和版本信息有可检查依据 |
| 阅读反馈 | 收藏、已读、相关 / 不相关 | 用户状态与中心采集状态互不混淆 |

### 阶段 C：形成持续研究与发布能力

目的：持续跟踪已研究项目，而不只是一次性发现。

- **版本跟踪**：加入已收录仓库的 Releases、提交或官方变更日志；变更与原研究版本建立关联。
- **专题汇总**：围绕“本地模型”“Agent 工具”“内容采集”等主题，汇总现有子项目的已验证能力。
- **证据检索**：先做普通结构化检索，内容规模增长后再评估全文或向量检索；回答仍附版本和来源。
- **精选传播**：发布人工审核过的专题文章和分享卡片，保留原文引用；传播效果单独记录。

验收不以“生成了多少文字”为目标，而看已验证项目是否更新及时、重复工作是否减少、读者是否能找到原始证据。

## 5. 建议跟踪的指标

以下是未来统计口径，目前没有数值基线，不虚构提升比例：

| 指标 | 计算 / 观察方式 |
| :--- | :--- |
| 采集成功率 | 按来源统计成功请求与预期采集次数，并区分无新内容 |
| 内容延迟 | 原始发布日期到成功采集 / 交付时间的差值 |
| 来源有效率 | 人工认为值得进一步查看的条目占采用样本的比例 |
| 摘要事实错误 | 抽样核对错误数字、错配来源、遗漏限制和虚构引语 |
| 重复交付率 | 同一内容在同一用户和窗口内被重复发送的比例 |
| 研究转化 | 线索进入研究队列、形成已验证子项目的数量与原因 |
| 单批成本 | 请求、转录、模型 token、人工审核所消耗的资源 |

## 6. 本次选择

当前先沉淀来源、流程、配置方法、展示规范与可复现的核验工具。下一轮若进入实现，优先选择“历史存储＋完整生成执行器＋明确错误状态”；这些工作能直接解决本次确认的缺口，再支撑更完整的展示和分发。
